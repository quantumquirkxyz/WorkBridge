## Changes

- Added `apps/agent-runtime/src/matching`, the runtime half of spec #2's
  decision: *"apps/agent-runtime receives validated profiles and vacancies, then
  calls packages/solver."*
- `MatchingService.nominateForCandidate` / `evaluatePair` geocode the inputs,
  project the domain documents onto the solver contracts, and call
  `@puente/solver` `nominate` / `evaluateMatch`.
- `geocode.ts`: a `GeocodingPort` maps the textual domain `Location` onto the
  solver `GeoPoint`. The deterministic Panama catalog is the offline default; the
  Google Geocoding API answers when a key is set; failures fall back with a
  recorded `fallbackReason`.
- `config.ts`: `matchingConfigFromEnv` drives both the Distance Matrix routing
  port and the geocoding port from `GOOGLE_MAPS_API_KEY`, so the primary routing
  path is Google Maps when configured and the local matrix otherwise.
- `adapt.ts`: `JobRequirements -> SolverVacancy` (only `getRankableRequirements`,
  original wording preserved) and `CandidateProfile -> SolverCandidate`, with
  arrays copied so the solver cannot mutate caller state.
- **Skill-id bridge**: the profile layer emits `plp:*` ids while vacancy
  requirements carry the ESCO-shaped `PA-*` ids. `toSolverCandidate` re-matches
  each profile skill against the vacancy taxonomy; without it every mandatory
  comparison would fail.
- Blocked vacancies are skipped, not scored; a call with no rankable vacancy
  throws `MatchingInputError`.
- Exported the seam from `apps/agent-runtime` and declared `@puente/solver` as a
  workspace dependency; documented `GOOGLE_MAPS_API_KEY` in `.env.example` and the
  seam in `apps/agent-runtime/README.md`.
- Added 26 Vitest tests across `geocode`, `config`, `adapt`, and `service`.

## Remaining risk

- The Google Distance Matrix and Geocoding adapters are covered by injected-fetch
  tests, not live calls.
- `CandidateMatchContext` / `VacancyMatchContext` carry facts the solver needs but
  the profile/vacancy documents do not (schedule, salary, capacity, transport,
  availability, home location). They are explicit inputs today, not yet sourced
  from the preferences ticket (#7) or an extended `JobRequirements`.
- The workflow's `market_and_matching` step still uses the LLM path; it does not
  yet invoke `MatchingService`, which is wired but consumed through the exported
  seam.
