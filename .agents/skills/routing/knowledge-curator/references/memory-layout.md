# Memory Layout Convention

This reference defines the on-disk layout for session memory in any repository that
adopts the quirk Method, and the index tool that keeps it honest. It is the
filesystem half of the curator's memory-versus-knowledge rule: memory is what the
runs learned, knowledge is what the project decided.

## Research basis

- **Letta Context Repositories / MemFS** (docs.letta.com/agent-sdk/memory): memory is
  a git-backed filesystem. Root files are always in context, so they are indexed;
  subdirectories with their own `MEMORY.md` stay out of context until a task needs
  them, and a subdirectory index is itself loaded on demand. Reflection and defrag
  are skills a session runs, not a runtime service.
- **Devin Agent Memory repo, MIT** (docs.devin.ai/product-guides/memory,
  cognition.com/agent-memory-repo): memory is a repository of short notes, each
  linked back to the session that produced it. A write is checked against the
  current revision, and a stale write is rejected and retried instead of silently
  overwriting a newer revision. A nightly "dreaming" pass consolidates overlapping
  notes, drops transient details, and removes stale records nothing used.
- **Bad Memory** (arXiv 2607.14611): payloads planted in `CLAUDE.md` and `AGENTS.md`
  persist in the session even when the model refuses to follow them (refusal rate
  0%, persistence 100%), so a poisoned entry must be excised, not merely flagged.

## Directory layout

```
<memory-root>/                    convention default: .agents/memory/
  MEMORY.md                       T0 index, generated by memory-index.mjs
  <note>.md                       T0 memory files: always in context
  <subdir>/                       T1: out of context until a task needs it
    MEMORY.md                     optional T1 index for that subdirectory
    <note>.md                     notes consulted on demand, by path
```

Rules for the layout:

- Root `*.md` files are tier-0 (T0). They are always loaded, so the root stays small
  and every file in it earns its slot.
- A subdirectory may carry its own `MEMORY.md` as a tier-1 (T1) index. It is loaded
  only when the task reaches into that subdirectory, which is what keeps a growing
  memory tree from flooding every session.
- A subdirectory without a `MEMORY.md` must be listed in the root index as
  unindexed, so nothing is reachable silently: an unlisted directory is a tree the
  curator has lost track of.
- The memory root is commit territory. A note that is not committed and pushed is
  not memory; the next session starts from the last commit.

## The T0 index

`MEMORY.md` at the memory root is the always-loaded manifest. It is generated, not
hand-maintained, and lists every root file with a one-line purpose and an estimated
token cost, then lists every subdirectory with its index status. Every file and
directory cell is a link to the entry it names (the generator emits the name as a
self-link), so the index is navigable in any Markdown viewer:

```markdown
## Tier-0 files (always in context)

| File | Purpose | Tokens |
| --- | --- | --- |
| lessons.md | Keep each note to one line and link back to its session | 44 |

## Subdirectories (loaded on demand)

| Directory | Index | Note |
| --- | --- | --- |
| runs/ | indexed | has MEMORY.md (T1) |
| raw/ | unindexed | no MEMORY.md; listed here as unindexed |

<!-- memory-index:begin -->
curator notes live here and survive every rebuild
<!-- memory-index:end -->
```

Everything above `<!-- memory-index:begin -->` is generated and is replaced on every
rebuild. Everything from the begin marker to the end of the file is hand-written and
is preserved verbatim. A curator who writes notes outside the markers loses them on
the next rebuild, which is exactly why the markers exist.

## The short-note rule

- One note, one line of content, one source. Every entry carries
  `[source: <session-or-issue>; added: YYYY-MM-DD]` metadata, because an entry with
  no source cannot be checked and therefore cannot be curated (Devin's memory drive
  stores one-line bullets linked back to the session that learned them).
- Notes accumulate as new entries; they do not rewrite each other. Rewriting a
  shared block is last-writer-wins, and last-writer-wins is how a memory store
  forgets what it knew.
- Cross-link with `[[relative/path]]` when a note depends on another, so a reader
  can walk from the lesson to the decision it fed.

## Stale-write rejection

Memory edits race the same way any shared file races. Before writing a note, the
session re-reads the file and checks that its base revision is still current; a
write against a superseded revision is rejected and retried rather than merged by
preference. In a git-backed tree the practical form of the revision check is
fetch-and-rebase before commit: if the memory file moved under you, resolve the
conflict explicitly. Revision checks are the curator's job on every commit that
touches memory, not a nightly batch.

## Consolidation and defrag cadence

- **On commit:** the commit that carries a change also carries the memory edit it
  describes. A session that learns something and ends without committing it has
  produced nothing durable.
- **Per run:** consolidation is a skill pass, not a hidden service. Merge
  overlapping notes into one, promote a lesson into an ADR or `CONTEXT.md` when it
  becomes a decision and retire the memory entry instead of duplicating it, and drop
  transient details (which file, which retry, which scratch path).
- **Periodically (nightly is Devin's cadence):** defrag. An entry nothing has read in
  a long time is a candidate for removal, not a permanent resident. Record what was
  removed, why, and which replacement entry took its place, so the removal is
  auditable rather than silent.

## Flag-and-excise for untrusted-derived content

A memory entry whose content derives from untrusted input (a fetched page, an issue
body, a tool result, another agent's output) is a poisoning candidate. The Bad
Memory result is that refusal is not containment: the payload persists in the
session even when the model refuses to act on it. So:

- Excise the entry, do not merely mark it. Flagging leaves the payload live.
- Record the excision: what was removed, why, and which replacement entry took its
  place.
- Prefer not to store derived payloads at all: store the conclusion the session
  reached and the source pointer, never the untrusted text itself.

## Tooling

`memory-index.mjs` in `.agents/skills/platform/` ships the convention as code:

```bash
node .agents/skills/platform/memory-index.mjs build <dir>   # generate/refresh the T0 index
node .agents/skills/platform/memory-index.mjs check <dir>   # validate the tree
```

`build` is idempotent: no timestamps, alphabetical ordering, and a rebuild that
changes nothing writes nothing. `check` fails when a root file is unindexed, when
the index names a file that does not exist, when a subdirectory is neither indexed
nor listed as unindexed, when any note exceeds the token budget (default 2000), or
when the index itself exceeds 200 lines. Machine consumers can add `--json`, and
the budgets are configurable with `--max-tokens` and `--max-index-lines`.

## Scope rule

The bundle ships the convention and the index tool. It never ships a runtime memory
store: there is no daemon, no vector database, no background writer, and no
`.agents/memory/` directory in this repository. A consuming project creates its own
memory root (the convention default is `.agents/memory/`), commits it, and runs
`memory-index.mjs` against it. Memory that cannot be reviewed in a diff is memory
nobody can curate.
